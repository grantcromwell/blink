My first attempt was with an IDO-SBC2D06, but I couldn’t find its stock firmware online from a reliable source, so I went with the Raspberry Pi 4 to handle keyboard inputs from the host machine. I flashed Debian 12 onto a microSD card, changed the boot configuration to enable UART, and added a dual-role data condition for the USB-C power port to enable serial communication over USB-C instead of using it only for power. After that, I added a serial login service for debugging over USB-C at 115200 baud, which would later caused issues. The screen command wasn’t initially working, so I added two new modules, Gserial and DesignWare. This fixed the problem and allowed the Pi to run in peripheral mode and communicate over USB-C. I used a microSD card I found lying around the house that I knew had Debian 12 on it and didnt think much of it. When gadget mode began working, it prompted me for a password, which I completly forgot about. I didn't realized the image on the sdcard might have a password. Throughout the troubleshooting process, I wondered if I was just better off quitting and using a esp32 with micropython but I decided that I should just continue and maybe think of that next time. When I was reconfiguring a passwordless login in the root filesystem of the sd card, I thought about it even more. After some time spent debugging, the serial console worked without a password. I then began to work on the application to drive a blinking LED on the pico over UART. I tried to use artificial intelligence to help generate boilerplate code for the bridge script that ran on the Rasberry pi 4 but most of the time it would get confused on which hardware protocols I was intending to use or it would lie about pinouts. I ended up revising majority of the boilerplate. At first, when I tried to use rshell to copy over the files to the pico it wasnt working, but then I realized there was a lingering screen process that was preventing me from copying the files over. After killing that process I was able to copy over the led script to the rasberry pico. My next issue was getting the bridge script to run indefinitely on the Rasberry pi. At first, the host to Rasberry Pi login service was interfering with communication from the Raspberry Pi 4 to the Pico, but after changing the login service baud rate to 9600 and creating a background service to always run the bridge script even through restarts, I was able to get it working. This broke my ability to use screen, but by the time I realized this, the script already worked. Once the baud rate issue was corrected, the bride script ran on the rasberry pi and communication over uart to the pico was correctly blinking inputs in morse code. The LED then began blinking when the host script was ran and characters were entered into the program.

First, I cloned Buildroot. I used Codex to review the default configuration and check whether serial support and Python software packages were available and enabled. When I found they weren’t, I added them to the Buildroot configuration. I used the make menuconfig command to add Python 3. This is when I learned the difference between linux-menuconfig and menuconfig.

 Next, I ran 'make linux-menuconfig' and I was honesty surprised to see how long it took it took to compile everything before populating the menu. When it did, I was stuck in the general setup menu for a while, but eventually I navigated to the device drivers section.
 It took time to work through all the options, but eventually I was able to add the configurations I needed. My main issue after the first flash was that I didnt have a communication package for transferring files and was missing a login shell. I had to edit the configuration files again to add getty and a file-transfer package, which took a while. When the login screen started working, I got an error while trying to copy the Python script to the Raspberry Pi. After installing the same communication package on the host machine, file transfers began working. After more troubleshooting with virtual serial port enumeration, I was able to get the GPOS build to run a Python script on the Raspberry Pi, which communicated with the Raspberry Pi Pico to blink the LED.


V2: Switching to two Arduino Nano Esp32s:
When I first switched to two Arduino Nano ESP32s, I was able to get UART communication working between them. The first ESP32 sent a message to the second to turn an LED on, then sent another message telling it to turn the LED off. The next step was to display a 1 or a 0 on an I2C display whenever the first ESP32 sent a messege to turn the LED on or off.
At first, I thought the display was broken because it wouldn’t show an I2C memory address, so I assumed the screen could be broken. To test this, I used a multimeter to check whether the ESP32’s 3.3V pin was supplying voltage. To my suprise it definitatly was, but the actual reading was 3.24V. Next, I checked the display’s VCC pin and found that it wasn’t receiving voltage. For a while, I couldn’t figure out what the problem was. Then I realized the display might require 3.3V at minimum. Since the ESP32’s output was 3.24 V, I decided I should attempty to power the display using another microcontroller that supplies more voltage. I ended up using a Raspberry Pi Pico, which supplies an actual voltage of5.12V on its VBUS pin, and after testing the pins of the I2C display with a multimeter, I saw that the screen was recieving voltage.
